## Аутентификация и базовый адрес

Ключ передаётся заголовком `x-access-key`. Получить — в кабинете на
https://hikerapi.com.

```bash
export HIKER_API_KEY="..."

curl -s "https://api.instagrapi.com/v2/user/by/username?username=example" \
  -H "accept: application/json" \
  -H "x-access-key: $HIKER_API_KEY"
```

Базовый адрес по умолчанию `https://api.instagrapi.com`. У сервиса есть второй
домен, но он закрыт защитой от ботов, которая режет обычные запросы из скриптов
(urllib, requests) — поэтому скрипты ходят на `api.instagrapi.com`.
Переопределяется переменной `HIKER_BASE_URL`.

Баланс и остаток запросов:

```bash
curl -s "https://api.instagrapi.com/sys/balance" -H "x-access-key: $HIKER_API_KEY"
```

Ключ — секрет. Только через переменные окружения, никогда в коде, в логах и в
отчётах.

## Что стоит денег, а что нет

Тарификация — **за запрос**, порядок ~$0.001 на распространённых тарифах
(сверь со своим в кабинете). Отсюда главный вывод для пайплайна:

**Платится не за поле, а за вызов.** Значит важно, сколько данных приходит за
один вызов.

| Данные | Приходят | Отдельный запрос? |
|---|---|---|
| Юзернейм, имя профиля, приватность | внутри страницы списка подписчиков/подписок | **нет — бесплатно в составе списка** |
| Описание профиля (био), категория, число подписчиков | только из запроса профиля | **да, 1 запрос на аккаунт** |
| Рилсы аккаунта | из запроса клипов, ~12 на страницу | да |
| Комментарии | отдельный запрос, ~15 на страницу | да |

На этой асимметрии и построен весь выигрыш скилла: список отдаёт имя даром,
описание — за деньги, поэтому грубый отсев делается по имени, а описание
запрашивается только для выживших. На реальном прогоне это превратило $37 в
$0.06.

## Эндпоинты, которые использует скилл

| Эндпоинт | Зачем в пайплайне |
|---|---|
| `GET /v2/user/by/username?username=` | юзернейм → числовой `pk` |
| `GET /v2/user/by/id?id=` | профиль по `pk`: био, подписчики, категория, приватность |
| `GET /v2/user/following?user_id=` | снежный ком: на кого подписан конкурент |
| `GET /v2/user/followers?user_id=` | подписчики эталонного аккаунта |
| `GET /v2/user/clips?user_id=` | рилсы аккаунта, ~12 на страницу |
| `GET /v2/media/info/by/code?code=` | метаданные ролика + ссылка на видеофайл |
| `GET /v2/media/comments?media_id=` | комментарии — там ищется отклик на кодовое слово |
| `GET /v2/hashtag/by/name?name=` | хэштег → `id` |
| `GET /v2/hashtag/medias/recent?hashtag_id=` | свежие публикации под хэштегом |
| `GET /v2/fbsearch/reels?query=` | поиск рилсов по запросу |
| `GET /v2/fbsearch/accounts?query=` | поиск аккаунтов по запросу |
| `GET /sys/balance` | остаток запросов и сумма |

Обращаться по числовому `pk` быстрее и надёжнее, чем по юзернейму: юзернеймы
меняются, идентификаторы — нет. Поэтому `pk` стоит сохранять в кэше.

## Формы ответов

Формы отличаются между версиями эндпоинтов: часть отдаёт объект напрямую, часть
заворачивает его в `response`. Не завязывайся на одну форму — ищи поле в обеих.
В `scripts/hiker.py` это делает `unwrap()`.

Поля медиа тоже приходят под разными именами:

| Смысл | Возможные имена |
|---|---|
| просмотры | `play_count`, `view_count` |
| подпись | `caption.text`, `caption_text` |
| время публикации | `taken_at`, `taken_at_ts` |
| ссылка на видео | `video_url`, `video_versions[0].url` |
| курсор следующей страницы | `next_page_id`, `next_max_id`, `end_cursor` |

Нормализация в одну плоскую форму — `media_fields()` в `scripts/hiker.py`.
Из `code` собирается публичная ссылка: `https://www.instagram.com/reel/{code}/`.

## Пагинация

Курсор из ответа передаётся параметром `page_id` в следующий запрос:

```bash
curl -s "https://api.instagrapi.com/v2/user/clips?user_id=123&page_id=CURSOR" \
  -H "x-access-key: $HIKER_API_KEY"
```

Порядок величин: рилсы ~12 на страницу, комментарии ~15, списки подписчиков и
подписок обычно 50-100 (замерь на первом вызове — от этого напрямую зависит
стоимость обхода). Помощник `paginate()` в `scripts/hiker.py` перебирает
страницы, пока есть курсор и данные, с потолком по числу страниц.

## Грабли

**Закреплённые рилсы идут первыми.** Эндпоинт клипов отдаёт закреплённые записи
в начале, ломая хронологию. Нельзя останавливать пагинацию на первом «старом»
ролике — так теряется всё, что за ним. Читай фиксированное число страниц и
фильтруй по времени публикации после.

**Просмотры иногда нулевые.** На части ключей `play_count` приходит нулевым
независимо от реальной статистики. Ноль — это чаще «не отдали», чем «не
смотрели». Такие ролики отбрасывай из выборки, иначе они утащат медиану вниз и
создадут фальшивые всплески у соседей.

**Ссылки на видео подписанные и протухают за часы.** Хранить их бессмысленно и
вредно (это ещё и не то, что стоит класть в отчёт). Скачивай сразу; 403 при
скачивании означает протухшую ссылку — перезапроси метаданные.

**Приватные и удалённые аккаунты.** Приходят как 404 или пустой объект. Клиент
возвращает `{}` на 404, чтобы это не роняло прогон — обрабатывай как «нет
данных», а не как ошибку.

**429 и 5xx.** Транзиентные. Экспоненциальный откат уже в клиенте; не увеличивай
число ретраев — уменьшай `--rps`.

**Поисковые эндпоинты отдают разнородные объекты.** В выдаче встречаются и
пользователи, и медиа с вложенным `user`. Разбирать надо оба варианта — это
делает `iter_users()` в `scripts/seed_pool.py`.

## Чего в API нет

Важно знать до того, как пообещаешь результат:

- **охваты, досматриваемость, удержание, переходы по ссылке** — это данные
  кабинета владельца аккаунта, наружу они не отдаются никем. Просмотры ≠ охват;
- **личные сообщения и заявки** — сколько людей написало кодовое слово в личку,
  снаружи не видно. Видно только след в комментариях, и это нижняя оценка;
- **поиск по описанию профиля** — искать по тексту био нельзя. Можно получить
  био уже известного аккаунта. Поэтому фильтр по имени — не оптимизация, а
  единственный доступный путь;
- **история метрик** — API отдаёт срез на сегодня. Динамика получается только
  собственными регулярными срезами. Это и есть причина, по которой скилл
  устроен как радар, а не как разовый отчёт;
- **демография аудитории** — пол, возраст, гео подписчиков недоступны.
